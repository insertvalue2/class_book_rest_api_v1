18장. 역할 기반 접근 제어란?

1. 역할의 개념

1.1 역할과 권한(GrantedAuthority)

15장에서 만든 인가 검사는 "이 글을 쓴 사람인가"만 확인합니다. 그런데 블로그 운영자는 남의 글도 지울 수 있어야 합니다. 글마다 작성자를 비교하는 방식으로는 이 규칙을 나타낼 수 없습니다. 회원이 어떤 종류의 사용자인지 따로 정해 두고, 그 종류를 기준으로 접근을 허락해야 합니다.

역할(role)은 회원에게 붙이는 사용자 종류의 이름입니다. 이 장에서는 일반 회원에게 USER, 관리자에게 ADMIN을 붙입니다. 한 회원이 역할을 여러 개 가질 수 있으므로 관리자는 USER와 ADMIN을 함께 가집니다. 이렇게 역할을 기준으로 주소 접근을 허락하거나 막는 방식을 역할 기반 접근 제어(RBAC, Role-Based Access Control)라고 합니다.

스프링 시큐리티는 역할을 따로 다루지 않고 권한(authority)이라는 더 넓은 개념으로 다룹니다. 권한 하나는 GrantedAuthority 인터페이스로 나타냅니다. 이 인터페이스에는 권한 이름을 문자열로 돌려주는 getAuthority() 메서드 하나만 있습니다. 14장에서 SecurityContextHolder에 넣은 Authentication 객체에는 사용자 정보와 권한 목록이 함께 들어갑니다. 주소별 접근 규칙을 검사하는 AuthorizationFilter는 이 권한 목록을 꺼내 규칙과 비교합니다.

구분이 책의 값쓰는 곳
역할USER, ADMINDB와 토큰에 저장
권한(GrantedAuthority)ROLE_USER, ROLE_ADMIN스프링 시큐리티의 접근 규칙 검사

14장의 인증 필터는 UsernamePasswordAuthenticationToken을 만들 때 권한 자리에 빈 목록 List.of()를 넣었습니다. 그래서 지금까지는 "로그인했는가"만 판단할 수 있었습니다. 이 장에서는 이 빈자리를 역할로 만든 권한으로 채웁니다.

1.2 hasRole과 ROLE_ 접두사

스프링 시큐리티에서 역할은 이름이 ROLE_로 시작하는 권한입니다. 이 약속을 ROLE_ 접두사라고 합니다. 주소 규칙에서 역할을 검사할 때는 hasRole()을 씁니다. hasRole()은 받은 이름 앞에 ROLE_를 붙인 뒤 권한 목록과 비교합니다.

기본 문법

Java
1 2
.requestMatchers("주소패턴").hasRole("역할이름")         // 권한 "ROLE_역할이름"이 있어야 통과
.requestMatchers("주소패턴").hasAuthority("권한이름")    // 권한 이름을 그대로 비교

hasRole("ADMIN")은 hasAuthority("ROLE_ADMIN")과 같은 검사입니다. 이 약속 때문에 이 장에서는 세 자리의 값을 서로 맞춰야 합니다.

자리쓰는 값잘못 쓰면
DB · 토큰의 역할ADMIN—
필터가 만드는 권한"ROLE_" + 역할 → ROLE_ADMIN접두사를 빼면 ADMIN 권한이 되어 hasRole("ADMIN")을 통과하지 못합니다
주소 규칙hasRole("ADMIN")hasRole("ROLE_ADMIN")으로 쓰면 스프링 시큐리티가 서버를 시작할 때 예외를 던집니다

가장 흔한 실수는 권한을 만들 때 ROLE_를 빠뜨리는 것입니다. 이때는 오류가 나지 않습니다. 관리자로 로그인해도 관리자 주소에서 403만 돌아와서 원인을 찾기 어렵습니다. 권한을 만들 때는 ROLE_를 붙이고, 규칙에는 접두사 없이 씁니다.

2. 회원에 역할 저장하기

2.1 @ElementCollection과 @CollectionTable

회원 한 명이 역할을 여러 개 가지므로 User에 List<String> roles 필드를 둡니다. 하지만 테이블의 한 칸에는 값을 하나만 넣을 수 있어서 목록을 user_tb에 바로 저장할 수 없습니다. 그래서 역할만 담는 테이블을 따로 만들고, 한 행에 "몇 번 회원의 역할 하나"를 저장합니다.

역할 하나는 문자열일 뿐이고 식별자(@Id)도 없으므로 엔티티로 만들 필요가 없습니다. 엔티티가 아닌 값의 모음은 @ElementCollection으로 매핑합니다. 값을 담을 테이블 이름과, 주인 엔티티를 가리키는 외래 키 열은 @CollectionTable로 정합니다.

package com.newtenco.blog.user;

import jakarta.persistence.CollectionTable;
import jakarta.persistence.Column;
import jakarta.persistence.ElementCollection;
import jakarta.persistence.Entity;
import jakarta.persistence.FetchType;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.GenerationType;
import jakarta.persistence.Id;
import jakarta.persistence.JoinColumn;
import jakarta.persistence.Table;
import lombok.Builder;
import lombok.Getter;
import lombok.NoArgsConstructor;
import org.hibernate.annotations.CreationTimestamp;

import java.sql.Timestamp;
import java.util.ArrayList;
import java.util.List;

@NoArgsConstructor
@Getter
@Entity
@Table(name = "user_tb")
public class User {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Integer id;

    @Column(unique = true, length = 20, nullable = false)
    private String username;

    @Column(length = 60, nullable = false)
    private String password;

    @Column(length = 30, nullable = false)
    private String email;

    @ElementCollection(fetch = FetchType.EAGER)
    @CollectionTable(name = "user_role_tb", joinColumns = @JoinColumn(name = "user_id"))
    @Column(name = "role")
    private List<String> roles = new ArrayList<>(List.of("USER"));

    @CreationTimestamp
    private Timestamp createdAt;

    @Builder
    public User(Integer id, String username, String password, String email, List<String> roles, Timestamp createdAt) {
        this.id = id;
        this.username = username;
        this.password = password;
        this.email = email;
        if (roles != null) {
            this.roles = roles;
        }
        this.createdAt = createdAt;
    }

    public void update(String email, String password) {
        this.email = email;
        this.password = password;
    }
}

2.2 역할을 즉시 로딩하는 이유

@ElementCollection의 기본 로딩 전략은 지연 로딩(LAZY)입니다. 5장에서 본 것처럼 지연 로딩은 값을 실제로 읽는 순간에 select를 보냅니다. 그래서 그 순간에 트랜잭션과 영속성 컨텍스트가 살아 있어야 합니다. 이 책은 open-in-view를 false로 두었으므로, 서비스 메서드가 끝난 뒤 컨트롤러나 필터에서 roles를 읽으면 지연 로딩이 실패합니다.

역할은 회원을 쓰는 거의 모든 곳에서 함께 필요합니다. 로그인할 때는 토큰에 역할을 담아야 하고, 역할을 바꾼 뒤에는 응답에 역할 목록을 담아야 합니다. 행 수도 회원 한 명에 한두 개뿐입니다. 그래서 fetch = FetchType.EAGER로 바꿔, 회원을 조회하면 역할도 바로 채워지게 했습니다.

즉시 로딩에도 비용이 있습니다. findById()로 회원 한 명을 찾을 때는 user_tb와 user_role_tb를 조인한 select 한 번으로 끝납니다. 하지만 JPQL로 회원 여러 명을 읽으면 회원마다 역할을 읽는 select가 따로 나갈 수 있습니다. 글 목록에서 join fetch b.user로 작성자를 함께 읽을 때도 같은 일이 생길 수 있습니다. 5장에서 @ManyToOne에 지연 로딩을 고른 이유와 같은 문제입니다. 역할은 작고 늘 필요한 값이라서 즉시 로딩을 골랐을 뿐이므로, 다른 연관관계에는 이 판단을 그대로 적용하지 않습니다. 회원을 조회할 때 실제로 어떤 쿼리가 나가는지는 show-sql 로그로 직접 확인할 수 있습니다.

3. 토큰에 역할 담기

DB에 저장한 역할은 요청이 올 때마다 권한 검사에 쓰여야 합니다. 그런데 14장에서 만든 인증 필터는 DB를 조회하지 않고 토큰만 보고 User를 만듭니다. 그래서 필터가 역할을 꺼내려면 역할이 토큰 안에 들어 있어야 합니다. 역할이 권한 검사까지 가는 길은 그림 18-1과 같습니다.

3.1 roles 클레임 쓰기와 읽기

java-jwt는 클레임 값으로 목록도 받습니다. 발급할 때는 withClaim("roles", 목록)으로 쓰고, 검증할 때는 getClaim("roles").asList(String.class)로 읽습니다.

package com.newtenco.blog.core.util;

import com.auth0.jwt.JWT;
import com.auth0.jwt.algorithms.Algorithm;
import com.auth0.jwt.interfaces.DecodedJWT;
import com.newtenco.blog.user.User;
import org.springframework.beans.factory.annotation.Value;
import org.springframework.stereotype.Component;

import java.util.Date;
import java.util.List;

@Component
public class JwtUtil {

    public static final String HEADER = "Authorization";
    public static final String TOKEN_PREFIX = "Bearer ";

    private final Algorithm algorithm;
    private final long expirationTime;

    public JwtUtil(@Value("${app.jwt.secret}") String secret,
                   @Value("${app.jwt.expiration-time}") long expirationTime) {
        this.algorithm = Algorithm.HMAC512(secret);
        this.expirationTime = expirationTime;
    }

    public String create(User user) {
        String jwt = JWT.create()
                .withSubject(user.getUsername())
                .withExpiresAt(new Date(System.currentTimeMillis() + expirationTime))
                .withClaim("id", user.getId())
                .withClaim("username", user.getUsername())
                .withClaim("roles", user.getRoles())
                .sign(algorithm);
        return TOKEN_PREFIX + jwt;
    }

    public User verify(String jwt) {
        DecodedJWT decoded = JWT.require(algorithm).build().verify(jwt);
        Integer id = decoded.getClaim("id").asInt();
        String username = decoded.getSubject();
        List<String> roles = decoded.getClaim("roles").asList(String.class);
        return User.builder().id(id).username(username).roles(roles).build();
    }
}

3.2 필터에서 권한 넘기기

토큰에서 꺼낸 역할 문자열은 스프링 시큐리티가 읽는 GrantedAuthority로 바꿔야 합니다. GrantedAuthority의 기본 구현체인 SimpleGrantedAuthority는 권한 이름 문자열 하나로 만듭니다. 1.2절의 약속대로 이름 앞에 ROLE_를 붙입니다.

import org.springframework.security.core.Authentication;
import org.springframework.security.core.context.SecurityContextHolder;

import java.io.IOException;

@RequiredArgsConstructor
public class JwtAuthorizationFilter extends OncePerRequestFilter {

    private final JwtUtil jwtUtil;

    @Override
    protected void doFilterInternal(HttpServletRequest request, HttpServletResponse response, FilterChain filterChain)
            throws ServletException, IOException {

        String header = request.getHeader(JwtUtil.HEADER);

        if (header != null && header.startsWith(JwtUtil.TOKEN_PREFIX)) {
            try {
                User user = jwtUtil.verify(header.substring(JwtUtil.TOKEN_PREFIX.length()));
                Authentication authentication =
                        new UsernamePasswordAuthenticationToken(user, null, user.getAuthorities());
                SecurityContextHolder.getContext().setAuthentication(authentication);
            } catch (JWTVerificationException e) {
            }
        }

        filterChain.doFilter(request, response);
    }
}

4.1 hasRole과 hasAnyRole

authenticated()로그인했다(권한은 보지 않음)이 장부터는 쓰지 않음

        source.registerCorsConfiguration("/**", config);
        return source;
    }

    @Bean
    public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
        http.headers(headers -> headers.frameOptions(frame -> frame.sameOrigin()));

        http.cors(cors -> cors.configurationSource(corsConfigurationSource()));

        http.csrf(csrf -> csrf.disable());
        http.formLogin(form -> form.disable());
        http.httpBasic(basic -> basic.disable());

        http.sessionManagement(session -> session.sessionCreationPolicy(SessionCreationPolicy.STATELESS));

        http.addFilterBefore(new JwtAuthorizationFilter(jwtUtil), UsernamePasswordAuthenticationFilter.class);

        http.exceptionHandling(ex -> ex
                .authenticationEntryPoint((req, res, e) -> RespFilter.fail(res, 401, "로그인 후 이용해주세요"))
                .accessDeniedHandler((req, res, e) -> RespFilter.fail(res, 403, "권한이 없습니다")));

        http.authorizeHttpRequests(auth -> auth
                .requestMatchers(HttpMethod.OPTIONS, "/**").permitAll()
                .requestMatchers("/join", "/login", "/check-username").permitAll()
                .requestMatchers("/h2-console/**").permitAll()
                .requestMatchers("/api/admin/**").hasRole("ADMIN")
                .requestMatchers(HttpMethod.GET, "/api/boards/**").permitAll()
                .requestMatchers("/api/**").hasAnyRole("USER", "ADMIN")
                .anyRequest().denyAll()
        );

        return http.build();

5.2 @NotEmpty와 허용 역할 검사

예제 18-8은 들어온 목록을 그대로 저장합니다. 그래서 {"roles": []}를 보내면 역할이 하나도 없는 회원이 생기고, 이 회원은 /api/**의 hasAnyRole("USER", "ADMIN")에 막힙니다. "MANAGER"나 소문자 "admin"처럼 이 서버가 모르는 값도 저장됩니다. 그래서 요청 값을 두 단계로 나눠 검사합니다.

첫 단계는 @NotEmpty입니다. 11장의 @NotBlank와 비슷한 제약 조건으로, 값이 null이거나 비어 있으면 검증에 실패합니다. @NotBlank는 문자열에만 쓰지만 @NotEmpty는 컬렉션에도 쓸 수 있습니다.

제약 조건실패하는 값쓰는 타입
@NotBlanknull, "", " "문자열
@NotEmptynull, 빈 문자열, 빈 컬렉션문자열 · 컬렉션 · 배열 · Map

두 번째 단계는 서비스에서 합니다. 어떤 역할을 허용할지는 서버가 정하는 규칙이기 때문입니다. 허용 역할을 Set으로 두고, 요청한 역할이 모두 그 안에 있는지 containsAll()로 확인합니다. 회원의 지금 역할과 똑같은 목록을 보낸 요청도 거절합니다. 비교하기 전에 요청 목록을 LinkedHashSet에 담으면 ["USER", "USER"] 같은 중복은 사라지고 순서는 그대로 남습니다.

package com.newtenco.blog.admin;

import com.newtenco.blog.board.Board;
import com.newtenco.blog.board.BoardRepository;
import com.newtenco.blog.core.handler.errors.BadRequestException;
import com.newtenco.blog.core.handler.errors.NotFoundException;
import com.newtenco.blog.user.User;
import com.newtenco.blog.user.UserRepository;
import com.newtenco.blog.user.UserRequest;
import com.newtenco.blog.user.UserResponse;
import lombok.RequiredArgsConstructor;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

import java.util.HashSet;
import java.util.LinkedHashSet;
import java.util.List;
import java.util.Set;

@RequiredArgsConstructor
@Transactional(readOnly = true)
@Service
public class AdminService {

    private static final Set<String> ALLOWED_ROLES = Set.of("USER", "ADMIN");

    private final BoardRepository boardRepository;
    private final UserRepository userRepository;

    @Transactional
    public void 관리자_게시글삭제(Integer id) {
        Board board = boardRepository.findById(id)
                .orElseThrow(() -> new NotFoundException("게시글을 찾을 수 없습니다"));
        boardRepository.delete(board);
    }

    @Transactional
    public UserResponse.RolesDTO 관리자_역할수정(Integer id, UserRequest.RolesDTO reqDTO) {
        User user = userRepository.findById(id)
                .orElseThrow(() -> new NotFoundException("회원을 찾을 수 없습니다"));
        Set<String> requestedRoles = new LinkedHashSet<>(reqDTO.roles());
        if (!ALLOWED_ROLES.containsAll(requestedRoles)) {
            throw new BadRequestException("역할은 USER, ADMIN 만 사용할 수 있습니다");
        }
        if (new HashSet<>(user.getRoles()).equals(requestedRoles)) {
            throw new BadRequestException("현재와 같은 역할입니다");
        }
        user.updateRoles(List.copyOf(requestedRoles));
        return new UserResponse.RolesDTO(user);
    }
}

5.3 바꾼 역할은 언제 반영될까?

다시 로그인해서 새 토큰을 받아야 반영됩니다. 역할을 바꾸면 DB는 바로 바뀝니다. 하지만 권한 검사에 쓰는 역할은 DB가 아니라 토큰에서 옵니다. 3절에서 본 것처럼 필터는 토큰의 roles 클레임만 보고 권한을 만듭니다. 그래서 이미 발급된 토큰에는 발급할 때의 역할이 그대로 남아 있습니다.

Postman에서 순서대로 확인합니다. 서버를 다시 띄워 ssar가 USER만 가진 상태에서 시작합니다.

순서요청결과
1ssar 로그인 → 토큰 A토큰 A의 roles: ["USER"]
2토큰 A로 GET /api/admin/hello403 "권한이 없습니다"
3cos 토큰으로 PUT /api/admin/users/1, {"roles": ["USER", "ADMIN"]}200, DB의 ssar 역할이 두 개로 바뀜
4토큰 A로 다시 GET /api/admin/hello여전히 403
5ssar 다시 로그인 → 토큰 B토큰 B의 roles: ["USER", "ADMIN"]
6토큰 B로 GET /api/admin/hello200 "관리자 ssar님 환영합니다"

역할을 올려 줄 때는 다시 로그인하면 되니 조금 불편한 정도입니다. 문제는 역할을 빼앗을 때 생깁니다. 관리자였던 회원에게서 ADMIN을 빼도, 그 회원이 가진 토큰은 만료될 때까지 계속 ROLE_ADMIN 권한으로 통과합니다. 12장에서 app.jwt.expiration-time에 정한 시간 동안은 그 회원이 관리자 API를 부를 수 있다는 뜻입니다. 토큰 방식은 요청마다 DB를 조회하지 않아서 빠르고, 이런 반영 지연은 그 대가입니다.

요청마다 DB에서 역할을 다시 읽으면 바로 반영되지만, 그러면 토큰 방식을 고른 이점이 줄어듭니다. 흔히 쓰는 방법은 액세스 토큰의 유효 시간을 짧게 잡아서, 역할이 반영되지 않는 시간을 몇 분 안으로 줄이는 것입니다. 유효 시간이 짧으면 사용자가 자주 다시 로그인해야 합니다. 이 문제를 푸는 리프레시 토큰은 19장에서 다룹니다.
