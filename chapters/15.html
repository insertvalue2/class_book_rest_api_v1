15장. 인가란?

14장에서는 요청에 실린 토큰을 검사해 누가 보낸 요청인지 알아냈습니다. 이 일이 인증(authentication)입니다. 이 장에서는 인증된 사용자가 요청한 일을 해도 되는지 따집니다. 이 일을 인가(authorization)라고 합니다. 로그인한 사람만 글을 쓸 수 있게 하고, 글을 쓴 사람만 그 글을 수정하고 삭제할 수 있게 만듭니다.

1. 글쓰기 API

1.1 로그인 사용자를 작성자로 연결

글을 저장하려면 작성자가 필요합니다. 작성자를 요청 본문의 userId로 받으면 클라이언트가 다른 사람의 번호를 넣을 수 있습니다. 그러면 남의 이름으로 글을 쓸 수 있게 됩니다. 그래서 작성자는 클라이언트가 보낸 값이 아니라 서버가 검증한 토큰에서 꺼냅니다.

14장의 인증 필터는 토큰을 검증한 뒤 토큰 정보로 만든 User 객체를 SecurityContextHolder에 저장합니다. 컨트롤러는 @AuthenticationPrincipal로 이 User를 바로 받습니다. 그래서 요청 본문에는 제목과 내용만 담고, 작성자는 토큰으로 정합니다.

글을 만들려면 Board에 값을 넣는 생성자가 있어야 합니다. 10장의 User처럼 @Builder를 붙인 생성자를 만듭니다. 요청 DTO SaveDTO의 toEntity()는 로그인 사용자를 받아 Board를 만듭니다.

@NoArgsConstructor
@Getter
@Entity
@Table(name = "board_tb")

    @Column(length = 1000, nullable = false)

package com.newtenco.blog.board;

import com.newtenco.blog.core.handler.errors.NotFoundException;
import com.newtenco.blog.user.User;
import lombok.RequiredArgsConstructor;
import org.springframework.data.domain.PageRequest;
import org.springframework.data.domain.Pageable;
import org.springframework.data.domain.Sort;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

@RequiredArgsConstructor
@Transactional(readOnly = true)
@Service
public class BoardService {

    private final BoardRepository boardRepository;

    public BoardResponse.PageDTO 글목록(Integer page, String keyword) {
        Pageable pageable = PageRequest.of(page, 3, Sort.by(Sort.Direction.DESC, "id"));
        return new BoardResponse.PageDTO(boardRepository.findAllJoinUser(keyword, pageable));
    }

    @Transactional
    public BoardResponse.ListDTO 글쓰기(BoardRequest.SaveDTO reqDTO, User sessionUser) {
        Board savedBoard = boardRepository.save(reqDTO.toEntity(sessionUser));
        return new BoardResponse.ListDTO(savedBoard);
    }

    public BoardResponse.DetailDTO 글상세(Integer id) {
        Board board = boardRepository.findByIdJoinUser(id)
                .orElseThrow(() -> new NotFoundException("게시글을 찾을 수 없습니다"));
        return new BoardResponse.DetailDTO(board);
    }
}

        return Resp.ok(boardService.글쓰기(reqDTO, sessionUser));
    }

    @GetMapping("/api/boards/{id}")
    public ResponseEntity<?> detail(@PathVariable("id") Integer id) {
        return Resp.ok(boardService.글상세(id));
    }

1.2 글쓰기 입력 검사

예제 15-1은 제목이 빈 글도 받습니다. 빈 문자열은 null이 아니라서 nullable = false에 걸리지 않고 그대로 저장됩니다. 반대로 title 키를 빼고 보내면 null이 DB 제약 조건에 걸려 500 오류가 납니다. 11장에서 회원가입에 쓴 Bean Validation을 글쓰기 요청에도 붙여 두 경우를 모두 막습니다.

길이 제한은 Board 엔티티의 @Column(length = 100), @Column(length = 1000)과 같은 값으로 맞춥니다. DB에 들어갈 수 없는 값은 DB까지 보내지 않고 400 응답으로 먼저 돌려보냅니다.

2. 작성자 검사

2.1 주소 규칙과 서비스 검사의 차이

글 수정과 삭제는 로그인만으로 허락할 수 없습니다. 로그인한 cos가 ssar의 글을 고치면 안 되기 때문입니다. 작성자 검사를 어디에 둘지 정하려면 주소 규칙과 서비스 검사가 각각 무엇을 알 수 있는지 비교해야 합니다.

구분주소 규칙(SecurityFilterChain)서비스 검사
실행 시점컨트롤러에 도착하기 전, 필터 단계서비스 메서드 안
판단 근거HTTP 메서드, 주소, 로그인 여부DB에서 조회한 데이터
답할 수 있는 질문"로그인한 사람인가?""이 글의 작성자인가?"
거절 응답RespFilter가 만드는 401 · 403예외를 받은 @RestControllerAdvice가 만드는 403

주소 규칙은 PUT /api/boards/1이라는 메서드와 주소만 봅니다. 1번 글을 누가 썼는지는 DB를 조회해야 알 수 있으므로 필터 단계에서는 판단할 수 없습니다. 그래서 "로그인했는가"는 주소 규칙이 맡고, "작성자인가"는 서비스가 맡습니다.

이 장에서 만들 수정 API는 PUT /api/boards/{id}, 삭제 API는 DELETE /api/boards/{id}입니다. 14장에서 정한 규칙 가운데 이 두 주소와 관계있는 줄은 다음 두 줄입니다.

코드 조각

Java
1 2
.requestMatchers(HttpMethod.GET, "/api/boards/**").permitAll()
.requestMatchers("/api/**").authenticated()

첫 줄은 GET 요청에만 맞는 규칙이므로 PUT과 DELETE 요청은 이 줄에 걸리지 않습니다. requestMatchers는 위에서부터 비교해 처음 맞는 규칙 하나만 적용합니다. 그래서 두 요청은 다음 줄 /api/**에 걸려 로그인이 필요한 주소가 됩니다. 주소 규칙은 이미 준비되어 있으므로 SecurityConfig는 고치지 않고 서비스 검사만 더합니다.

다른 자료에서는 메서드 위에 @PreAuthorize를 붙여 권한을 검사하는 코드도 자주 보입니다. 이 방식을 메서드 보안(method security)이라고 하며, 설정 클래스에 @EnableMethodSecurity를 붙여야 동작합니다. 이 책은 메서드 보안을 쓰지 않습니다. 접근 규칙이 SecurityFilterChain 한곳에 모여 있으면 규칙 전체를 한눈에 점검하기 쉽습니다. 작성자 검사는 어차피 DB에서 글을 꺼내야 하므로 서비스 코드 안에 두는 편이 읽기 쉽습니다.

2.2 ForbiddenException과 403

403 Forbidden은 "누구인지는 알지만 이 일은 허락하지 않는다"는 뜻의 상태 코드입니다. 401은 누구인지 모를 때, 403은 누구인지 알지만 권한이 없을 때 씁니다. 남의 글을 고치려는 사용자가 누구인지는 토큰으로 이미 알고 있으므로 이 경우에는 403이 맞습니다.

서비스가 이 상황을 알릴 수 있게 7장의 NotFoundException과 같은 모양으로 ForbiddenException을 만듭니다. 전역 예외 처리기에는 이 예외를 403 응답으로 바꾸는 ex403()을 더합니다.

서비스에서 던진 예외는 컨트롤러가 실행되는 중에 생기므로 @RestControllerAdvice가 받습니다. 14장의 accessDeniedHandler는 필터 단계에서 주소 규칙에 막혔을 때 실행됩니다. 둘 다 403을 돌려주지만 403을 만드는 위치가 다릅니다.

package com.newtenco.blog.core.handler;

import com.newtenco.blog.core.handler.errors.BadRequestException;
import com.newtenco.blog.core.handler.errors.ForbiddenException;
import com.newtenco.blog.core.handler.errors.NotFoundException;
import com.newtenco.blog.core.handler.errors.UnauthorizedException;
import com.newtenco.blog.core.util.Resp;
import lombok.extern.slf4j.Slf4j;
import org.springframework.http.HttpStatus;
import org.springframework.http.ResponseEntity;
import org.springframework.validation.FieldError;
import org.springframework.web.ErrorResponse;
import org.springframework.web.bind.MethodArgumentNotValidException;
import org.springframework.web.bind.MissingServletRequestParameterException;
import org.springframework.web.bind.annotation.ExceptionHandler;
import org.springframework.web.bind.annotation.RestControllerAdvice;

@Slf4j
@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(MethodArgumentNotValidException.class)
    public ResponseEntity<?> validation(MethodArgumentNotValidException e) {
        FieldError fe = e.getBindingResult().getFieldErrors().getFirst();
        return Resp.fail(HttpStatus.BAD_REQUEST, fe.getDefaultMessage());
    }

    @ExceptionHandler(MissingServletRequestParameterException.class)
    public ResponseEntity<?> missingParam(MissingServletRequestParameterException e) {
        return Resp.fail(HttpStatus.BAD_REQUEST, e.getParameterName() + ":값을 입력해주세요");
    }

    @ExceptionHandler(BadRequestException.class)
    public ResponseEntity<?> ex400(BadRequestException e) {
        return Resp.fail(HttpStatus.BAD_REQUEST, e.getMessage());
    }

    @ExceptionHandler(UnauthorizedException.class)
    public ResponseEntity<?> ex401(UnauthorizedException e) {
        return Resp.fail(HttpStatus.UNAUTHORIZED, e.getMessage());
    }

    @ExceptionHandler(ForbiddenException.class)
    public ResponseEntity<?> ex403(ForbiddenException e) {
        return Resp.fail(HttpStatus.FORBIDDEN, e.getMessage());
    }

    @ExceptionHandler(NotFoundException.class)
    public ResponseEntity<?> ex404(NotFoundException e) {
        return Resp.fail(HttpStatus.NOT_FOUND, e.getMessage());
    }

    @ExceptionHandler(Exception.class)
    public ResponseEntity<?> exUnknown(Exception e) {
        if (e instanceof ErrorResponse er) {
            HttpStatus status = HttpStatus.valueOf(er.getStatusCode().value());
            return Resp.fail(status, status.getReasonPhrase());
        }
        log.error("예상하지 못한 오류", e);
        return Resp.fail(HttpStatus.INTERNAL_SERVER_ERROR, "관리자에게 문의하세요");
    }
}

아직 ForbiddenException을 던지는 곳이 없어서 응답은 달라지지 않습니다. 3절의 글 수정 서비스가 처음으로 이 예외를 던집니다.

서비스의 작성자 검사는 항상 같은 순서로 진행합니다. 먼저 글을 찾고, 없으면 NotFoundException을 던집니다. 글이 있으면 글의 작성자 번호와 로그인 사용자 번호를 비교하고, 다르면 ForbiddenException을 던집니다. 글이 있는지 먼저 확인해야 없는 글을 요청했을 때 404 대신 "권한 없음"이 나가는 일을 막을 수 있습니다.

3. 글 수정

3.1 변경 감지(더티 체킹)

JPA로 글을 수정할 때는 update 쿼리를 직접 쓰지 않고 save()도 다시 부르지 않습니다. 트랜잭션 안에서 조회한 엔티티의 필드 값만 바꾸면, 트랜잭션이 끝날 때 JPA가 update SQL을 보냅니다. 이 기능을 변경 감지(dirty checking)라고 합니다.

5장에서 본 것처럼 JPA는 트랜잭션 안에서 조회한 엔티티를 영속성 컨텍스트(persistence context)에 보관합니다. 엔티티를 처음 담을 때는 그 순간의 값을 스냅샷(snapshot)으로 복사해 둡니다. 트랜잭션을 커밋하기 직전에는 엔티티의 지금 값과 스냅샷을 비교합니다. 값이 달라진 엔티티가 있으면 update SQL을 만들어 DB에 보냅니다.

변경 감지가 일어나려면 두 조건이 맞아야 합니다. 첫째, 엔티티를 같은 트랜잭션 안에서 조회해야 합니다. 트랜잭션 밖에서 new로 만든 객체는 JPA가 관리하지 않으므로 값을 바꿔도 아무 일도 일어나지 않습니다. 둘째, 쓰기 가능한 트랜잭션이어야 합니다.

두 번째 조건에서 실수가 잦습니다. BoardService 클래스에는 @Transactional(readOnly = true)가 붙어 있습니다. 읽기 전용 트랜잭션에서는 하이버네이트가 커밋할 때 바뀐 내용을 DB에 반영(flush)하지 않습니다. 수정 메서드에 @Transactional을 빠뜨려도 오류는 나지 않습니다. 응답에는 바뀐 값이 나오는데 DB의 값은 그대로 남습니다.

엔티티 값은 setter로 필드마다 바꾸지 않고, 바꿀 수 있는 필드만 받는 메서드를 엔티티에 둡니다. Board에 update(title, content)를 만들어 두면 글에서 바꿀 수 있는 값이 제목과 내용뿐이라는 것이 코드에 드러납니다.

3.2 @PutMapping과 UpdateDTO

@PutMapping은 HTTP PUT 요청을 메서드에 연결합니다. PUT은 주소가 가리키는 자원을 보낸 값으로 바꾸라는 요청입니다. 그래서 PUT /api/boards/1은 "1번 글을 이 내용으로 바꿔라"라는 뜻이고, 제목과 내용을 모두 받습니다.

요청 본문은 UpdateDTO로 받습니다. 지금은 SaveDTO와 필드도 검사 규칙도 같지만 하는 일이 다릅니다. SaveDTO는 toEntity()로 새 엔티티를 만들고, UpdateDTO는 이미 있는 엔티티에 넣을 값만 넘깁니다. 나중에 수정할 때만 받는 값이 생겨도 글쓰기 요청에 영향이 없도록 DTO를 따로 둡니다.

서비스의 글수정()은 2.2에서 정한 순서대로 글을 찾은 뒤 작성자를 검사합니다. 검사를 통과하면 board.update()만 부르고 save()는 부르지 않습니다.

4. 글 삭제

4.1 @DeleteMapping

@DeleteMapping은 HTTP DELETE 요청을 메서드에 연결합니다. DELETE /api/boards/1은 1번 글을 지우라는 요청이고, 본문 없이 주소만으로 지울 대상을 정합니다.

삭제도 글을 찾고 작성자를 검사하는 순서가 같습니다. 검사를 통과하면 JpaRepository의 delete()에 엔티티를 넘깁니다. 지운 뒤에는 돌려줄 글이 없으므로 서비스는 void를 반환하고, 컨트롤러는 Resp.ok(null)로 성공만 알립니다.

H2 메모리 DB는 서버를 다시 실행하면 data.sql의 샘플 데이터로 돌아갑니다. 그래서 지운 1번 글도 서버를 다시 켜면 되살아납니다.

delete()도 SQL을 바로 보내지 않습니다. 엔티티에 삭제 예정이라고 표시해 두었다가 트랜잭션을 커밋할 때 delete SQL을 보냅니다. 그래서 글삭제()에도 쓰기 가능한 @Transactional이 필요합니다.

지금은 글을 가리키는 다른 데이터가 없어서 글만 지우면 끝납니다. 16장에서 댓글이 글을 가리키게 되면 댓글이 달린 글을 지울 때 문제가 생깁니다. 이 문제의 해결 방법도 16장에서 다룹니다.
